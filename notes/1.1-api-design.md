## Design Decisions

### 1. Modelling a purchase
A purchase is a resource under the player. A player may have multiple purchases. This give us a history list, an easy single purchase lookup and a natural place for authorization.
We need to only send the item the player wants to buy. The server can fetch all the other information. Adding other fields, like cost, would open a vulnerability - a user could inject a lower price and get an item for a lower than intended cost. This way, this is server authoritative. 
Similarly, the player comes from the auth token, which is server issued and signed.
The response returns a new balance - so the client can display it -, purchaseId - useful for support ticket and retry logic and the item ID and cost to update the UI. 

### 2. Client retries after a timeout
We need to be able to distinguish between a retry of the same purchase vs a deliberate retry of a new purchase of the same item. To do this the client generate a key when the buy button is pressed, before the first send and reuses it on every retry of that purchase. The server stores the key and the playerId with the result and an expiry date. A retry with the same key returns the stored result instead of proceeding with the action.
A retry for a request that is still being processed should be rejected and return a 409 code. The same key with a different item should return 422 code

### 3. "Players around me"
We add the /global/ to the path to indicate to the server what leaderboard we are querying. If we later add a weekly, or per-country, we can then change the path and keep the same logic.
The server knows who is making the request via the auth token that accompanies this query. 
The default value is 25 and max range is 50. If a request exceeds the the range, we should return 400. We could clamp down to the maximum silently, but the client might not get what they are asking for. This was considered.
If the player has no score yet, we can return 404. If the player is has less than 25 player above their rank, then we should fetch the top 51.

## Interview questions

1. What does "stateless" mean for an HTTP API, and why does it matter for scaling? 
   1. Stateless means that each HTTP request must carry everything the server needs. The server does not maintain the context of previous requests. This also allowed for scalability - so a load balancer can send any request to any instance, and if one instance dies, no one loses their session.
2. Why is PUT idempotent but POST isn't? Is DELETE idempotent if the second call returns 404?
   1. PUT means "put this exact resource at this URL", POST asks the server to create something and the server picks up where it lives. Updating a value twice to the save value does not change the state, adding 2 entries does. Delete is idempotent if the second request return 404 - no change to the state happened.
3. 401 vs 403?
   1. 401 is Unauthorized; 403 is Forbidden. The difference is that 401 doesn't know who the requester is while 403 the requester is known. In the case of 401, the user can authenticate and retry. 403 logging in won't help 
4. When would you return 409 vs 422?
   1. 409 is returned when a valid request is received but it conflicts with the current state. An example is trying to add 2 username entries to a database that has a unique constraint in the username. 422 is returned when the user has made a request that violates a business rule: buying an item that is not for sale.   
5. PUT vs PATCH?
   1. PUT replaces a resource entirely; Any fields left out of the request are cleared. PATCH changes a resource partially, allowing the user to update selected fields of a resource. 
6. A client gets a 500 and a 400. Which one should it retry, and why?
   1. 500;  500 means something went wrong in the server. Many reasons why that could have happened and a retry might not encounter the same issue. 400 is caused by a bad request. Without the user changing anything, the request is the same, so still bad. <br> Note that retrying 500 is only safe if the operation is idempotent or carries an idempotency key, because the server might have completed the task before.
