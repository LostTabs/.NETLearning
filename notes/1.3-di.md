### What is a captive dependency, and how do you detect it, both at runtime and before it ships?

A captive dependency is a a dependency that lives as long as the service that depends on it does. The container can check this for us. ```ValidateScope``` throws when a singleton resolves a scoped service, and ```ValidateOnBuild``` checks the whole registration graph at startup.

### Explain transient, scoped and singleton, with an Arcadia example of each and the reason for the choice.

Transient is a dependency that creates an instance per resolution (everytime something asks). It should be used for stateless helpers and validators.
If accessed twice within the same request, it will be different instances. The only example of this in the project right now is ```TransientProbe```.
<br>Scoped is a dependency that is created per request.
If accessed twice within the same request, it will be the same, but different instances between requests. We have ```RequestContext``` as an example. We want the context of the request to stay the same, so scoped makes sense.
<br>Singleton is a dependency created by the root provided and that instance is used for the whole app.
This is always the same instance. An example of this would be ```InMemoryPlayerRepository```, which we want to last the entire livecycle of the app.

### Why is DbContext scoped? What specifically breaks as a singleton, and what breaks as transient?
A DbContext is a unit of work and an identity map. Both need to match one per request. As transient, 2 repositories in the same request would get different contexts; They couldn't share tracked entitites or save in one transaction.
As a singleton, concurrent requests share one non-thread-safe object, which causes InvalidOperationExceptions under load, the change tracker keeps growing, so memory climbs and you read stale data and it holds on to the request it was created in, so things like the current player identity are simply wrong for everyone after that first request.

### A BackgroundService needs to write to the database every minute. How do you get a DbContext into it correctly?
It should create a scope for each unit of work.

### Validation catches scoped-in-singleton but not transient-in-singleton. When is the second one actually a bug?
When the transient has a per-use state. As an example of this, the transient probe is captures by the app for the endpoint /di/lifetimes. When evaluating it, it returns different things. If we want it to return the same thing - keep a state - its transient life cycle would be a bug.
We saw validation catching scoped-in-singleton when creating a leaderboard (singleton) that consumed RequestContext (scoped) - ```Cannot consume scoped service 'Arcadia.Api.Infrastructure.RequestContext' from singleton 'Arcadia.Api.Leaderboards.LeaderboardCache'.```

### Who disposes services the container creates? What goes wrong if you resolve a disposable transient from the root provider?
The container owns disposal of what it creates. If we resolve a disposable transient from the root provider, it's tracked until the app shuts down, which is a slow memory leak.

### Should ValidateScopes be on in production? What does it cost?
Yes. It might make deploy slower, but its an extra layer of security and validation of the code.
