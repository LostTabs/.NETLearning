### What is a captive dependency, and how do you detect it, both at runtime and before it ships?


A captive dependency is a dependency that lives in longer-lived service than itself. In Development, the container can 
check this for us, but it does not check for transient-in-singleton. 
```ValidateScope``` throws when a singleton resolves a scoped service, and ```ValidateOnBuild``` checks 
the whole registration graph at startup. On Production, we need to enable flags for this to happen.
<br>ValidateOnBuild should be on in every environment, in addition to tests present in CI.

### Explain transient, scoped and singleton, with an Arcadia example of each and the reason for the choice.

Transient is a dependency that creates an instance per resolution (everytime something asks). It should be used for 
stateless helpers and validators.
If accessed twice within the same request, it will be different instances. The only example of this in the project 
right now is ```TransientProbe```.
<br>Scoped is a dependency that is created per request.
If accessed twice within the same request, it will be the same, but different instances between requests. We have 
```RequestContext``` as an example. We want the context of the request to stay the same, so scoped makes sense.
<br>Singleton is a dependency created by the root provided and that instance is used for the whole app.
This is always the same instance. An example of this would be ```InMemoryPlayerRepository```, which we want to last the 
entire livecycle of the app as it *is* the data the app is manipulating. On singletons we also need to be aware of
thread safety - We are using ConcurrentDictionaries in that class for this reason.

### Why is DbContext scoped? What specifically breaks as a singleton, and what breaks as transient?
A DbContext is a unit of work and an identity map. Both need to match one per request. As transient, 2 repositories in 
the same request would get different contexts; They couldn't share tracked entitites or save in one transaction.
As a singleton, concurrent requests share one non-thread-safe object, which causes InvalidOperationExceptions under 
load, the change tracker keeps growing, so memory climbs and you read stale data. In addition, Singletons are always
constructured by the root provider, including their dependencies. If it has a RequestContext, this is created
by the root provider, and the RequestContext belongs to no context, causing the singleton to read nulls.

### A BackgroundService needs to write to the database every minute. How do you get a DbContext into it correctly?
It should create a scope for each unit of work by injecting an IServiceScopeFactory - this is a singleton, so its 
safe to hold. On each tick, we can create a scope and resolve the DBContext from it, disposing of it at the end.
We could use IDbContextFactory as an alternative.

### Validation catches scoped-in-singleton but not transient-in-singleton. When is the second one actually a bug?
A transient has a per-use state. It is not a bug when its stateless and thread-safe. It becomes a bug when it's not
thread-safe, holds a per-use state or owns resources that should be disposed of after each request - like a connection.

### Who disposes services the container creates? What goes wrong if you resolve a disposable transient from the root provider?
The container owns the disposal of the services it creates. Resolving disposable transients  from the root provider 
would make them effectively singletons - lasting as long as the app lifetime. This could lead to slow memory leaks as 
more and more transients become effectively singletons.

### Should ValidateScopes be on in production? What does it cost?
Yes. It will make each request slower - which is why its off by default - as it needs to check every service resolution,
but guaratees correctness. As of note, ValidateOnBuild does not consider scoped-in-singleton a bug, as that depends
on the use case.
