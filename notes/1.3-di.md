### What is a captive dependency, and how do you detect it, both at runtime and before it ships?

A captive dependency is a dependency that lives in longer-lived service than it'self. This forces a shorter-lived 
service to live as long as the service that is holding it. In Development, the container can check this for us, 
but it does not check for transient-in-singleton. 
<br>```ValidateScopes``` throws when a singleton resolves a scoped service, and "ValidateOnBuild checks at startup that 
every service can be constructed; with ValidateScopes also on, the lifetime check runs at startup too.
On Production, we need to enable flags for this to happen.
<br>ValidateOnBuild should be on in every environment, in addition to integration tests that build the real host so
validation runs on every PR.

### Explain transient, scoped and singleton, with an Arcadia example of each and the reason for the choice.

Transient is a dependency that creates an instance per resolution (every time something asks). It should be used for 
stateless helpers and validators.
If accessed twice within the same request, it will be different instances. The only example of this in the project 
right now is ```TransientProbe```.
<br>Scoped is a dependency that is created per request.
If accessed twice within the same request, it will be the same, but different instances between requests. We have 
```RequestContext``` as an example. We want the context of the request to stay the same, so scoped makes sense.
<br>Singleton is a dependency created by the root provider and that instance is used for the whole app.
This is always the same instance. An example of this would be ```InMemoryPlayerRepository```, which we want to last the 
entire lifecycle of the app as it *is* the data the app is manipulating. On singletons we also need to be aware of
thread safety - We are using ConcurrentDictionaries in that class for this reason.

### Why is DbContext scoped? What specifically breaks as a singleton, and what breaks as transient?

A DbContext is a unit of work and an identity map. Both need to match one per request. As transient, 2 repositories in 
the same request would get different contexts; They couldn't share tracked entities or save in one transaction.
As a singleton, concurrent requests share one non-thread-safe object, which causes InvalidOperationExceptions under 
load, the change tracker keeps growing, so memory climbs and you read stale data. In addition, Singletons are always
constructed by the root provider, including their dependencies. This means that we would have a single DbContext
for every request, never disposed of until the app shutdown, causing a memory leak.

### A BackgroundService needs to write to the database every minute. How do you get a DbContext into it correctly?

It should create a scope for each unit of work by injecting an IServiceScopeFactory - this is a singleton, so it's 
safe to hold. On each tick, we can create a scope and resolve the DBContext from it, disposing of the scope at the end, 
which disposes the context.
<br> We could use IDbContextFactory as an alternative. We can't just inject DbContext as hosted services are singletons,
so the DbContext would be captured and validations thrown.

### Validation catches scoped-in-singleton but not transient-in-singleton. When is the second one actually a bug?

A Transient-in-singleton is not a bug when it's stateless and thread-safe. It becomes a bug when it's not
thread-safe, holds a per-use state or owns resources that should be disposed of after each use - like a connection - 
because, once injected into a singleton, it becomes effectively a singleton.

### Who disposes services the container creates? What goes wrong if you resolve a disposable transient from the root provider?

The container owns the disposal of the services it creates.
<br>
Each resolution of a disposable transient creates a new instance. If the creator of these new instances is the root
provider, it keeps a reference to those instances, which causes them to not be garbage collected.
<br>
Also, note that instances passed by me (```AddSingleton(TimeProvider.System)```) are never disposed of by the container.

### Should ValidateScopes be on in production? What does it cost?
`ValidateScopes` makes the container throw when a scoped service is resolved by a
singleton or from the root provider. When it's on, this check runs on every service
resolution at runtime. If `ValidateOnBuild` is also on, it additionally runs once at
startup for every registered service. The cost is a small check on every resolution
for the lifetime of the app, which is why Microsoft turns it off by default in Production.

The startup check doesn't make the runtime check redundant, because `ValidateOnBuild`
only sees constructor parameters. It can't see inside factory registrations
(`sp => ...`) or services resolved at runtime with `GetRequiredService`. 

So the real question is whether a scope bug could reach Production without ever being
resolved in Development or tests. Arcadia has no integration tests or CI yet, so I'd keep
it on in Production: a loud exception is better than silently shared state, and the
overhead is small. Once integration tests build the real host with validation on and
exercise every endpoint in CI, those tests catch the same bugs before deploy, and I'd
turn it off in Production to save the per-resolution cost.
