### 1 - In what logical order is a SELECT evaluated, and why does that stop you using a SELECT alias or a window function in WHERE?

The logical order is FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> window functions -> DISTINCT -> ORDER BY ->
LIMIT.
WHERE runs before SELECT, so an alias present in SELECT does not exist when WHERE is being evaluated. Similarly,
window functions are also computed  after WHERE. HAVING is also affected by the same thing, for the same reason,
To filter, we should compute it in a CTE or subquery and then use that value on the where of the outer query.

### 2 - What's the difference between WHERE and HAVING? Give an Arcadia query that needs both.

WHERE is used to filter rows. HAVING is used to filter groups. HAVING runs after GROUP BY and can filter based on those
groups, while WHERE can not due to the logical sequence.
If we extend query 9 (items owned by at least 3 distinct players) to be "Items owned by at least 3 distinct players 
that are worth more than 100 coins", we could use the current HAVING implementation and extend it using a WHERE that 
filters items worth less than 100 coins.

<code>SELECT it.id, it.sku, COUNT(*) AS owners_count 
<br>FROM inventory inv JOIN items it ON it.id = inv.item_id
<br>WHERE it.price_amount > 100 AND it.price_currency_code = 'COIN'
<br>GROUP BY it.id
<br>HAVING COUNT(*) >= 3
<br>ORDER BY owners_count DESC, it.id; </code>

### 3 - Why does a WHERE condition on the right-hand table turn a LEFT JOIN into an INNER JOIN? Use your query 5.

When you use a `LEFT JOIN`, every row on the left table ar kept. When there is no match, the right hand column are `NULL`.
If we apply a `WHERE` on top of a `LEFT JOIN`, the `WHERE` only return values that evaluated to true, and comparing something
to `NULL` return unknown, so it gets filtered out.

You can see that happening on V1 of query 5: all the players with no entries in player balance have `NULL` as a value
so they get filtered out, instead of having a value of 0.


### 4 - When do NOT IN and NOT EXISTS give different answers?

Both are Anti-joins. However, 'NOT IN' can cause bugs if the subquery ever returns 'NULL' as comparing anything with 
'NULL' returns 'unknown' which causes the entire expression to be 'unknown'. This causes NOT IN to return no rows at 
all. NOT EXIST does not have this problem. In general, `NOT EXISTS` is the better option.

### 5 - RANK, DENSE_RANK or ROW_NUMBER: which would you use for Arcadia's leaderboard, and why? Consider what a player sees when two players are tied.
ROW_NUMBER is the number of the row in the window's `ORDER BY`. The tied positions are arbitrary unless we add a tie-breaker.
RANK show the rank of the players based on a specific value (in Arcadia examples, we use the leaderboard score). If we have
a tie, the player would see 1->2->2->4 which indicates to the player in the 4th place they still have 3 players
ahead of them.
`DENSE_RANK` can still show ties, but does not skip ranks, so instead of the previous example, we would see 1->2->2->3.
This would lead the player in th 4th place to think they have only 2 players ahead of them, which incorrect.
So, I would use RANK to display and ROW_NUMBER with a tie-breaker for positions and pagination.

### 6 - Is a CTE faster than a subquery in Postgres?
Neither is inherently faster. A CTE reference once is inlined and get the same plan as the equivalent subquery.
Before Postgres 12, CTEs where always materialized, so they couldn't be optimized due to it being an optimisation fence.
After 12, CTE are inlined so its optimized like a subquery, if they are only referenced once. This is relevant as Query 12 references player_coin_value 
CTE twice, so by default it gets materialized - its result is computed once and reused. The fastness of CTE's depend on 
the case - is it inlined, or materialized. Note that you can override either default and force it to be - or not be - 
materialized.
CTE should be used not for speed but for readability. They allow to build queries in named steps, as we can see on Query
12 and 15.

### 7 - What's the difference between COUNT(*), COUNT(col) and COUNT(DISTINCT col)? Show where each gives a different number in your data.

COUNT(*) counts rows. We used this on Query 6 to determine the player count per country. COUNT(col) counts rows where
a col is not NULL. We used this on Query 2 to determine that amount of distinct items each player had. The fact
it ignores NULL is useful, as we can simply LEFT JOIN players with inventory. Players with no Inventory get NULL values 
on the inventory cols, simplying and making the query more readable.
COUNT(DISTINCT col) counts distinct non-null values. We did not us this in our queries, but an example would be "list 
the number of countries that have Arcadia players"
SELECT COUNT(Distinct p.country)
FROM players p;

Now that we have the definitions, lets look at an example where they show different values:
SELECT p.country,
COUNT(*)                      AS joined_rows,
COUNT(inv.item_id)            AS items_owned,
COUNT(DISTINCT inv.player_id) AS players_with_items
FROM players p
LEFT JOIN inventory inv ON inv.player_id = p.id
GROUP BY p.country
ORDER BY p.country;

RESULT:
country | joined_rows | items_owned | players_with_items
---------+-------------+-------------+--------------------
GB      |         149 |         149 |                 50
GR      |           4 |           4 |                  2
IE      |         150 |         150 |                 50
PT      |         141 |         139 |                 51
UK      |           5 |           5 |                  3
US      |         134 |         134 |                 52

COUNT(*) counts all of the joined rows. If a player has no inventory, they still get added to the count.
COUNT(inv.item_id) counts only the number of rows that have items. So players with no inventory get excluded due
to the LEFT JOIN adding `NULL` values to them.
COUNT(DISTINCT inv.player_id) counts only the number of rows for distinct players. If a player has multiple items, they
get collapsed into a single entry for the purpouses of the count.
