### Pooling. What happens when you call OpenConnectionAsync, and what happens when you dispose the connection? What happens when the pool runs out of connections, and what usually causes that? Use your 218 ms versus 4 ms measurements.

OpenConnectionAsync borrows an idle physical connection, or creates one if none are idle and the pool isnt full. Dispose
just resets and returns the connection to the pool, not closing it, available for the next job. We can see
this behaviour in action when running requests after booting up the API - the first time we connect it took 218ms -
this is mostly because it had to open the physical connection- it needs to  start the TCP connection, TLS handshake, 
authentication process. The second request took 4.49ms because it used the connection that already existed in the pool.
If all connections are busy/lent out, the next OpenAsync waits. If none become available within the timeout window,
it throws. By default, Npgsql pool allows for 100 connections per data source - that is per app instance. Postgres
allows - by default - 100 connections, but this is server wide. Three API instances could generate 300 connections
and the server would start refusing the extra ones.
The main cause for pools to run out connections is forgetting to dispose of connection: the pool slowly drains,
and requests start timing out under load. Another reason could be holding connections for too long with slow queries.
A defense against this is the rule of "open late and dispose early".


### Lifetimes. Why is NpgsqlDataSource a singleton, while connections live only for one operation? What would have gone wrong with the scoped data source you registered in Step 2, both at startup and at runtime?

NpgsqlDataSource owns the pool. Its thread-safe and expensive to create. If it wasn't a singleton, the pooling feature 
wouldn't work, as it would be disposed of after each request - So each request would need to create its own data source, 
start the connection, etc, paying the full cost of the connection. Also, the moment we DI the data source into the
repository, it would result in an error that would stop the app from starting. ValidateScopes together with 
ValidateOnBuild would detect singleton holding a scoped service and stop the start up. However, if the repository
was also scoped, it would start up without any problems, but the users would experience slow requests.
The connections on the otherhand are a per-operation use. Its cheap, not thread safe and can not be used by multiple
users at the same time - leading to the issue of the pool drying if too many connections are hold for too long.

### Parameterisation. How do parameterised queries prevent SQL injection? What is actually sent to Postgres? Why isn’t “escaping the quotes myself” a real defence? What can’t be parameterised, and how would you handle a client-chosen sort column?

How it prevents injection. A parameterised query keeps the structure of the query separate from the data. The SQL text 
is fixed in my code, with placeholders where values go. Postgres parses the text and decides the query’s structure 
before it sees any value. User input can change what the query compares against, but never what the query does.

What is sent to Postgres. I write WHERE username = @username. Npgsql rewrites that to WHERE username = $1 and sends the 
SQL text and the values in separate protocol messages. The value never becomes part of the SQL text. My debug endpoint
shows this. After the fix, the payload ' OR username LIKE '%' returned [], because Postgres compared the whole string,
quotes included, against username as one literal value, and no player has that name. The stacked UPDATE payload didn’t 
run either. There was no second statement, just one long, odd-looking username.

Why escaping quotes isn’t a real defence. Escaping is still building SQL from strings, so I’d have to predict every 
way the parser could read the input, and missing a single case leaves me injectable. Not every value sits inside quotes. 
Take WHERE id = {id} with an input of 1 OR 1=1: there’s no quote to escape, and it still returns every row. The rules 
also depend on context. A string literal, a LIKE pattern and an identifier each need different handling. With
parameters, the value is never parsed, so there’s nothing to escape.

What can’t be parameterised, and the sort column. Only values can be parameters. Table names, column names, and keywords
such as ASC and DESC are part of the query’s structure. For a client-chosen sort, I map the client’s input to SQL that 
I wrote myself. For example, "score" maps to score and "date" maps to created_at, and the direction maps to ASC or DESC. 
Anything else gets a 400, or falls back to a default sort. The client’s text never enters the SQL. This has to be an 
allowlist, not a blocklist. A check like “letters only” still lets the client name any column, including ones I never 
meant to expose, and a blocklist only stops the attacks I thought of in advance.

### Blast radius. Your injection was in a debug endpoint. Why can one injectable query compromise the whole database, and what limits the damage if a mistake like this ever reaches production?

Injected statements, no matter where the endpoint is, runs with whatever privileges the app's database user has.
We used a read-only search enpoint to run an UPDATE.
In our case the Docker-created user is a superuser: it can drop any table, and COPY ... TO PROGRAM runs shell commands 
on the database server, which takes the attacker from owning the data to owning the machine It goes from
the attacker owning the data to owning the machine itself.
Beyond making sure that we don't allow for injectable query, a second line of defense is least privilege. The app
connects as a role that can only SELECT, INSERT and UPDATE the tables it needs to access, leaving migrations with a 
separate, more privileged role that the running app never uses. Other defense layers to 
consider would be passwords being stored hashed, regular backups and a database that isn't reachable from the internet.

### Async I/O. Why should database calls be async in an API? What does async improve, and what does it not improve? Answer at the level of the Learn section; the internals come in 2.1.

Database calls are mostly waiting for the network. During the await time, the thread goes back into the pool, allowing
the API to serve other requests. It improves concurrency of the server. What it does not improve is the speed at
which the query is made. 
Keep in mind that the pool - by default - will still only have 100 connections, so the 101st concurrent query still 
waits for a free connection. The difference is that, with async, it waits without blocking a thread.
Cancellation token should always be passed as part of each request as a wait to recover connections belonging to requests
that were dropped - either because the client timed out or disconnected.

### Dapper. What does Dapper do for you, and what doesn’t it do? What trap does it have with interpolated strings? Use your own exploit code as the example.

Dapper is a set of  extension methods on DBConnection, and does things like turning anonymous objects into parameters
and mapping results columns onto types by name, replacing the ADO.NET boilerplate, like DBCommand, DBParameter and 
Execute reader.
It doesn't track changes, write SQL or do migrations. This is good in the sense that the developer owns the queries -
its correctness, performance and safety - but as a trade-off, it does not catches mistakes.
Dapper does not parameterise C# interpolate strings. It allows for plain string concatenation and injection, let we did
with our exploitable end point, where we were able to pull the entire collection of emails without knowing any username
by simply injecting a query into the string interpolation:
```var sql = $"SELECT id AS PlayerId, username FROM players WHERE username = '{username}'";```
C# builds the interpolated string first, and the Dapper receives it as one finished string, so Dapper can’t tell which 
part came from the user and has nothing to parameterise.
We can fix this issue by using parameterization:
```const string sql = "SELECT id AS PlayerId, username FROM players WHERE username = @username"; var command = new CommandDefinition(sql, new { username }, cancellationToken: token);```

### Constraints over checks. CreateAsync never checks whether a username exists before inserting. How does it still return 409 with the right message, and why is that better than checking first? Also explain why your ids jumped from 211 to 215.

Having the API checking for the existence of a username - which should be unique - does not guarantee uniqueness
against concurrency. If we have 2 concurrent requests, they both might read at the same time, see it as available, try 
to insert and the constraint rejects the second one, forcing us to handle the constraint error anyway. The check
added a roundtrip but safeguarded nothing.
The only way to guarantee this is at the Database level, hence why the constraint is necessary.
It returns a 409 with the right message because the repository catches PostgresExceptions from the database - in 
this case, the error thrown when a duplicated username is trying to be added, using when to filter the SQL state -, 
parses it and maps it into a CreateUserStatus, and the endpoint turns each status into a 409 and its own message.
Although the id column is GENERATED ALWAYS AS IDENTITY which is sequencial in its generation, its not transactional. 
When an insert calls nextval, that number gets used even if the transaction fails or rolls back. So, the first user
was successful inserted, so they took 211, then there were 3 insert failures that took 212,213 and 214, and then
another success that goes to 215. This is intended behaviour and Ids should never be assumed to be contiguous
Forcing it to be  transactional would cause inserts to be serialised - every insert would need to wait until all 
previous ones commit or roll back.
