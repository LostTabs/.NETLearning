### What is the difference between a primary key and a unique constraint? (I'll probe the NULL behaviour and what foreign keys can reference.)

A Unique constraints is a constraint that forces a rule on a table that no two rows may have the same value. 
There is no limit to the amount of unique constratains on a table.  By default each NULLS count as different from 
every other NULL. Postgres 15+ supports UNIQUE NULLS NOT DISTINCT, which makes NULLS count as equal to eachother. 
Finally, uniqueness is an exact-match - meaning case sensitive.

A primary key is a row identifier and implicitly not null. Each table contains at most one primary key.
Both primary keys and unique constraint values can be used as foreign keys. In fact, foreign keys only need to be values
that guarantee uniqueness, so each reference points at exactly one row. A primary key can span several column - composite keys.

### What problem does normalisation solve? Use the anomalies, with an Arcadia example rather than a textbook one.
Normalisation is the process of splitting tables until each column depends only on its key. Normalisation solves 3 problems:
- Update anomaly: Updating a value requires updating every row that contains that value. If we have our inventory stored
as a flat table, if the username changes, we would need to update every row that contains that value, or the database
would disagree with itself. Same would apply if we change the currency of a specific item, or its cost.
- Insert anomaly: We cant add new items into the system without someone owning them first. Instead of having a table
where all items are defined - like we do now - we would need a player to own them first so we can insert them
into the inventory.
- Delete anomaly: Deleting rows can remove concepts from the database. For instance, if currencies were not normalised,
if every item that uses coins as its currency gets deleted, then the concept of "coins" as a currency in the database
disappears.

Normalised data costs more to read because of joins, which is why denormalising on purpose is sometimes worth it.

### Why did you choose bigint or UUID for players.id? What would make you change your mind?
I choose bigint for this example because it is small and sequential which makes it cheap to index. The project is quite 
small, with one database so it's fit for purpouse. 
UUID can be generated anywhere - client code, another service, etc. 
But its double the bytes against bigint, and that increase is felt across every foreign key and every index. UUID v4 
scatter inserts across the index; v7 is time-ordered which fix this.
As it currently stands, I dont see any advantages to move to UUID that outweight the cost yet.
Player Ids are created by the database when the player is created and are carried by the JWT - so everyone else
receives the id from it.
I would change from bigint to UUID if generating the id outside of the database is important and/or if the number
of entries on the table was information I wouldn't want to leak - because bigint is sequential, by probing that number
a competitor could figure out how many players I have, and guessable, so player 42 could try to probe player 43.
We can use authorization to cover against that.


### player_balances is denormalised. What could go wrong, and which future lesson fixes it?
When a player buys something, we will need to update both the balance and ledger that contains the history of 
transactions for the player. 
Say that a crash happens between both operations, then we could have a database that either debited the players but
didn't credit the currency to them - which is a bad experience for the player - or we credited the player but the debit
didn't happen - which would be considered an exploit and bad for the business. 
It could also open the door to a situation where 2 concurrent purchase requests that exceed the balance of the player.
The first one credits the players, then the second credits the player, then the first does the debit, and the second 
debit tries to do it and fails because of the "no negative balance" constraint. Now you have a situation where the balance
says ne thing, but the ledger adds to a different value. There will be a fix for this in lesson 1.8.
More importantly, the reason *why* it was denormalised should be stated: Instead of deriving the balance of a player
by calculating the entire ledger, its much faster and less expensive to just have that value maintained in parallel.

### Why does UNIQUE in the database matter even if your API checks "username taken?" first?
Because API checks do not guarantee uniqueness against a race condition situation. 2 concurrent requests, being handled
by different threads, both can see "no" and both insert. It also cover for human error: and SQL query runned by hand or
a future admin tool, the constraint protects the data. Constraints are the DB level is the only thing that guarantees 
this because it checks at the moment of writing. Once the API see this unique violation it should return with a 409 
Conflict instead of a 500.
