### Walk me through what happens between a request hitting Kestrel and your handler running. Mention your middleware, routing, and how your playerId and request body get into the handler.

Kestrel is a built-in webserver. It listens on a port, parses raw HTTP bytes into a HttpContext object and hands each request into the app. The HttpContext enter the middleware pipeline, where the routing middleware looks for the path and method and picks the matching endpoint. For instance, GET /players/{playerId}/profile would get {playerId}'s profile. Middleware after routing, such as authentication and authorization can see which endpoint was chosen and act on it. PlayerId get parsed from the route. The request body is deserialized into one of the request classes and passed down to the handler. My custom middleware runs first and the final response passes through it.

### Minimal APIs vs controllers: when would you choose each?

Controllers give you filters, conventions, and automatic model validation ([ApiController] returns 400 for you), plus a natural way to group many related actions into a class. They make sense in large APIs and for teams that know them.
<br>Minimal APIs have less ceremony, lower overhead, and work better with Native AOT. Endpoint filters and route groups cover most of what controllers offered.
<br>Match the existing codebase; for a new service, Minimal APIs are a good default. For this project, since it was being developed from the ground up, minimal APIs made sense.

### IOptions vs IOptionsSnapshot vs IOptionsMonitor? Also say which one you used for the leaderboards, and whether it was the right choice.

IOptions is read once at startup, IOptionsSnapshop is read once per request and IOptionsMonitor is always urrent, with change notifications. For the leaderboards we used IOptions, which is defendable since there is a case to be made that the Limits and Ranges that were decided before deployment shouldn't be changed - say that they feed into some UI that is not prepared to deal with more, we don't want those values to change.
<br>On the other hand, there is an argument to use IOptionsSnapshop. The fact they are read once per request allow us to change the values on the fly, without requiring a redeployment of the app. Say the client app UI had an update that now supports a different range of entries, we can adjust to that without having to redeploy the app.
IOptionsMonitor is not a good option for this use case because we dont need live updates. Unless there was a specific design decision - which there wasn't - that required those values to be more mutable, it wouldn't bring any benefits.
